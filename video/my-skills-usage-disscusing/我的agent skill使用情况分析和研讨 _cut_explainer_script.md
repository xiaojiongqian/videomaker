## Skill 的结构与设计原则
@range 00:02:30-00:05:00
- 解释一个 skill 的基本构成：Markdown、脚本、参考资料和可选资产。
- 好的 skill 不是一次写完，而是要通过测试和迭代不断调优。
- workflow pattern、review pattern、pipeline pattern 都可以封装成 skill。
- 私有领域知识最适合沉淀成 skill，便于团队共享。

## 实战一：内容创作类 Skill
@range 00:05:00-00:07:30
- 展示自己做的小说与内容生产类 skill 作为真实案例。
- 主 skill 负责编排，sub-agent 或子 skill 分别处理对白、润色、审计等角色。
- 第一版看上去很完整，但实际效果一般，暴露出闭环不足的问题。
- 这段重点不是展示产物，而是说明“设计之后必须继续迭代”。

## 实战二：QA 与冒烟测试流水线
@range 00:07:30-00:10:00
- 把测试前置条件、账号、环境变量、预期结果交给 skill 管理。
- 用 suite 的方式组织回归和冒烟测试，让一次执行覆盖多个关键路径。
- 功能点和预期结果可以先结构化，再交给 AI 自动生成测试动作。
- 目标是让 AI 连续执行验证，而不是每一步都靠人工盯着点。

## 契约、Lint 与模块边界
@range 00:10:00-00:12:30
- 为 AI 开发建立更强的契约约束，而不仅是传统 lint。
- 单向依赖、模块边界、接口约束都应该变成机器可检查的规则。
- 一旦 AI 改动破坏了规则，lint 和测试应当立即暴露问题并促使修复。
- 这让“先拆小模块，再逐步扩展”成为更可执行的工程策略。

## 重构策略与护栏演进
@range 00:12:30-00:15:00
- 接口稳定后，内部实现可以大胆替换，旧系统也可以逐步重构。
- 不只是新功能可以用 AI，老代码的结构清理和替换同样适合。
- 当模型能力更强时，过多护栏反而会拖慢效率，需要动态调整。
- 这里强调的是“先稳住边界，再逐步放开自动化权限”。

## 重复工作、SQL 与工具化扩展
@range 00:15:00-00:17:30
- skill 很适合吸收重复提示词和重复动作，减少反复灌输上下文。
- Web 程序、非 Web 程序、SQL 驱动任务都可以通过 skill 接入工具链。
- 像数据收集、财务处理、规则化操作，本质上都可以变成可执行流程。
- 前提是模型接入要稳定，否则整个自动化链条会变得脆弱。

## 非编程场景与 Agent 基础设施
@range 00:17:30-00:20:00
- skill 不只服务编码，也可以用于业务决策、office hours、Git 操作等场景。
- 趋势不是“让人迁就工具”，而是为 agent 构建更友好的工作接口。
- GitHub、脚本、命令行、第三方库这些能力都可以被重新包装成 skill。
- 总结来看，skill 的价值在于把方法、约束和经验沉淀成可复用系统。
